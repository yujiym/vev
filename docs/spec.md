# vev — AI-assisted Live Visual Sequencer

The specification: what vev is, and how it is meant to work. It is the authority the code answers to, and the document every milestone is read against.

Status as of 2026-09-28: M0 (§18) is built — the workspace, the Worker, the SPA and the gate. Everything beyond it is design, not description. §17 lists what is still unverified; the items M0 settled say so.

## 0. Overview

vev is a web app for live VJ performance that chains saved visual clips (Hydra / textmode.js / ISF). A decision model suggests about three candidates for the next clip. By default the top candidate plays next, but the performer can click any candidate to choose it deliberately. Transitions between clips have defaults, and are changed automatically according to the structure of the track.

### Background and references

- https://blog.amagi.dev/entry/jev-vj — uses Jev only to _suggest_ clips; a human performs the actual switch. vev rebuilds this idea with live-coding visual engines and a pluggable decision-model layer.
- Problems in the original article and how vev addresses them:
  - Clip descriptions were written by hand → clips are _code_, so descriptions are generated by an LLM from the code (ISF clips already carry metadata).
  - Context length (112 clips ≈ 27k tokens) → embedding search narrows the library to the top K candidates before the decision model is called.

### Project facts

- License: **AGPL-3.0-or-later** for the whole monorepo (see §14.1)
- Free and open source; no hosted multi-tenant service. **Each user self-hosts vev on their own Cloudflare account.**
- Repository: GitHub account `yujiym` (`yujiym/vev`) — a personal project, not a company one
- Official site: **https://vev.0x7.sh** — docs, demo tracks (read-only), setup guide. It is the upstream author's own deployment, not a shared service; `SOURCE_URL` defaults to the upstream repository.

### Design principles

1. **The decision model suggests; the human decides.** Auto-advance is only a default and can always be overridden.
2. **Never stop the show.** Playback continues if the backend, the decision model, or the network fails.
3. **Local-first capable.** Venue networks are unreliable; vev must be able to run fully locally (including the decision model).
4. **License metadata always travels with the clip.**

## 1. Scope

### In the MVP

- Three engines: Hydra, textmode.js (+ textmode.synth.js), ISF
- Clip library (registration, automatic annotation, thumbnails)
- Tracks (ordered clips): create, save, share via public URL
- Live screen: current clip, next clip, three candidates, transitions
- Separate output window (projector) and control window
- Audio input (FFT) and BPM (tap tempo)
- Candidate generation: embedding search → re-ranking by a decision model
- Steering chat: a standing direction, in words, that biases which clips are offered (§8.6)
- Decision providers: **Cloudflare Workers AI (`typesafe/jev`) by default**, other System One–compatible endpoints (Kev, TypeSafe direct, OpenRouter, etc.) configurable in settings
- Automatic transition selection (rules + decision model)
- Credit display and a commercial-use filter
- Self-hosting: one-command setup and a "Deploy to Cloudflare" path
- Local mode: the built app runs on the performer's own machine at a venue, with no internet (§15.3)
- AGPL compliance built in (source link in the UI, third-party notices)

### Later

- MIDI controller mapping, MIDI clock, Ableton Link
- Third-party clip submissions (security reasons, see §13)
- Fine-tuning a decision model on vev's own logs (logging starts in the MVP)
- Additional engines: p5.js, Three.js, raw GLSL (Shadertoy-style)
- Dynamic visual generation: clip code written by a model, before or during a set (§11.2 says what the MVP does now so that this stays possible)

## 2. Glossary

| Term | Meaning |
| --- | --- |
| Clip | One visual. Has an engine, code, metadata and license |
| Engine | Runtime that renders a clip: `hydra` / `textmode` / `isf` |
| Track | Ordered list of clips, plus per-transition settings and section labels |
| Section | Label for a region of a track (intro / build / peak / break / outro, or free text) |
| Candidate | A suggested next clip, with a score from the decision model |
| Transition | How clip A switches to clip B (cut / crossfade / modulate …) |
| Session | One live performance. All actions and suggestions are logged |
| Compositor | Layer that mixes engine outputs into the final output (Hydra `o0`) |
| Decision provider | A configured endpoint that answers System One–style typed questions |
| Direction | A standing instruction from the steering chat that biases candidate selection until it is replaced or cleared (§8.6). Not a command: it never moves the show by itself |
| Local mode | How vev runs at a venue: the built app on the performer's machine, local D1 / R2 / KV, the `local` decision profile, no internet. Not development (`pnpm dev`, HMR, a dev server in front of the Worker) |

## 3. Architecture

vev is a single Cloudflare Worker (Hono + static Svelte SPA) plus Cloudflare data services. The default decision model is Jev via the Workers AI binding, so **no extra infrastructure is needed in the default setup**. Other decision endpoints (e.g. a self-hosted Kev) can be added in settings; a self-hosted endpoint can be exposed through Cloudflare Tunnel, or reached on localhost in local mode.

### Separate output window

- The control UI opens the output window with `window.open()`; it is made fullscreen on the projector.
- **The show renders only in the output window** (no duplicate WebGL contexts for playback).
  - **Registration is the one exception, and it is transient.** The registration screen (§11) has to run a clip to validate it and to record its thumbnail, and only a browser can do that (§11.1). It therefore mounts a transient `HydraCompositor` of its own — in fact two in sequence and never at the same time: the probe's, disposed the moment the probe returns (pass or fail), then the recording's, which renders the thumbnail, samples the palette and is **disposed immediately** in a `finally`, before the clip is saved. The cap that matters is §6.5's on _live_ contexts; a context that exists for a few seconds on a screen where nothing is playing does not compete with the show. Nothing else in the control UI renders: the control window's monitor of the output is downscaled frames, not a second context.
- Control ↔ output state sync uses `BroadcastChannel` (same browser, no network).
- The control UI shows a low-resolution monitor of the output (downscaled frames sent periodically, or `captureStream`).
- Running control and output on different machines (Durable Objects + WebSocket) is out of MVP scope.

### Local mode

At a venue the same built Worker runs on the performer's machine under a local workerd, with no internet and no Cloudflare services behind it. See §15.3.

## 5. Data model

```ts
type EngineKind = 'hydra' | 'textmode' | 'isf'

interface Clip {
  id: string // opaque and permanent; never parsed. Tracks, logs and Vectorize all hold it
  slug: string // human-readable, changeable: "hydra/khoparzi-aquatic-blubs"
  engine: EngineKind
  title: string
  code: string // normalized code
  originalCode: string // code as imported (including license header)
  params: ClipParam[] // externally controllable params (ISF INPUTS / Hydra macros). Nothing detects
  // these yet — through M2 every clip's `params` is `[]`

  // Automatic annotation (editable by a human). Every field here is absent until annotation has
  // run — annotation is asynchronous and must never block registration (§0 principle 2, §11.1) —
  // so anything reading them must handle a clip that has none. `annotationStatus` says which case
  // a row is in. See ADR 0005 for why five of the seven are asked as typed questions.
  annotationStatus: 'pending' | 'ok' | 'failed'
  description?: string // visual description (color, shape, motion) — the one generated field
  tags?: string[] // "kaleidoscope", "noise", "ascii", ... — from the fixed vocabulary, plus the two derived from deps
  palette?: string[] // dominant colors (hex), read from the frames the clip actually rendered (§11)
  energy?: 1 | 2 | 3 | 4 | 5
  motion?: 'static' | 'slow' | 'medium' | 'fast'
  density?: 'sparse' | 'medium' | 'dense'
  layerHint?: 'bg' | 'fg' | 'any'
  defaultBars: number // default length for auto-advance, in bars — declared at registration, not annotated

  // Runtime requirements (detected at ingestion)
  deps: {
    usesFeedback: boolean // e.g. src(o0)
    outputsUsed: string[] // ["o0"] / ["o0","o1"] ...
    sourcesUsed: SourceReq[] // cam / video / image / screen
    usesAudio: boolean // a.fft etc.
    extensions: string[] // external scripts via loadScript
  }
  isolated: boolean // needs its own engine instance

  // Provenance and license
  origin: 'imported' | 'authored' | 'generated'
  derivedFrom?: string[] // clip ids this one was built from (a mutation, a remix)
  generator?: {
    // origin "generated" only; §11.2
    model: string
    prompt: string
    at: number
  }
  author: string
  sourceUrl?: string
  license: string // an SPDX id, a licence name ("CC BY-NC-SA 4.0"), or "unknown" — never empty (§14.2)
  commercialOk: boolean
  modified: boolean

  thumbnailKey?: string // R2 object key of the short looping video — a KEY, not a URL: a URL bakes a
  // hostname into a stored row, and the same row has to resolve under the deployed Worker, a preview
  // and local mode. The URL is built where it is served, from `GET /media/:key` — mounted outside `/api/*`, so a thumbnail renders for a viewer with no owner login (§13). Absent until a
  // thumbnail has been recorded; a clip with no thumbnail also has no `palette` (§11).
  reviewed: boolean // checked by a human
}

interface Track {
  id: string
  slug: string // for the public URL
  title: string
  ownerId: string
  visibility: 'private' | 'unlisted' | 'public'
  bpmDefault?: number
  mode: 'noncommercial' | 'commercial' // commercial excludes clips with commercialOk = false
  items: TrackItem[]
  defaultTransition: TransitionSpec
}

interface TrackItem {
  clipId: string
  bars?: number // defaults to clip.defaultBars
  section?: string // "intro" | "build" | "peak" | "break" | "outro" | free text
  transitionIn?: TransitionSpec // automatic if omitted
  transitionLocked?: boolean // true = never changed automatically
  paramOverrides?: Record<string, number>
}

interface TransitionSpec {
  type: 'cut' | 'crossfade' | 'modulate' | 'feedbackMelt' | 'luma' | 'diff' | 'asciify'
  bars: number // 0 = immediate
  easing?: 'linear' | 'easeInOut' | 'expo'
}

interface CandidateResult {
  clipId: string
  score: number // probability from the decision model (used for ranking only)
  source: 'decision' | 'embedding' | 'fallback'
  providerId?: string // which decision provider produced it
  reason?: string // short UI text, generated by rules (tag match, energy…)
  suggestedTransition?: TransitionSpec
}

interface SessionEvent {
  // everything is logged (future fine-tuning data)
  sessionId: string
  t: number
  kind:
    | 'candidates_shown'
    | 'candidate_selected'
    | 'auto_advanced'
    | 'transition_changed'
    | 'chat_message'
    | 'direction_changed'
    | 'panic'
    | 'param_changed'
    | 'provider_fallback'
  payload: unknown
  state: DecisionState // snapshot of the state at that moment
}
```

Decision-provider configuration is described in §8.4.

## 6. Engine adapters

All engines implement one interface and **only render into their own surface**. Mixing is the compositor's job.

`source()` returns a `TextureSource` (a canvas, a video element, or a `MediaStream`) rather than an `HTMLCanvasElement`, because a clip that has to be isolated may not be able to hand over a canvas at all: today that is an `isolated` Hydra instance, later a sandboxed renderer for generated or third-party code (§11.2, §13), which can only pass a stream across the boundary.

```ts
interface EngineAdapter {
  kind: EngineKind
  prepare(clip: Clip): Promise<void> // compile / load assets (done before playback)
  start(): void
  stop(): void // stop the render loop (always when not visible)
  setParam(name: string, value: number): void
  setGlobals(g: { bpm: number; energy: number; fft: Float32Array; time: number }): void
  source(): TextureSource | null // canvas | video | MediaStream; null inside the main Hydra instance
  dispose(): void
}
```

### 6.1 Hydra

- One main Hydra instance acts as **both the compositor and the runtime for Hydra clips**.
- Output buffers:
  - `o0`: final output (compositor)
  - `o1`: current clip (A)
  - `o2`: next clip (B), used during transitions and for preloading
  - `o3`: spare (intermediate buffer for transitions, etc.)
- **No live previews of the three candidates.** Candidate cards show thumbnail videos (saves buffers and GPU).
- Clip code is normalized at ingestion (§11). At runtime `.out()` is rewritten to `.out(o1)` / `.out(o2)`.
- Clips that use several outputs internally (`deps.outputsUsed.length > 1`) are marked `isolated`. They run in a separate Hydra instance (`makeGlobal: false`) on their own canvas, fed back through an `s` source. This requires code rewriting and may be excluded in the MVP (show a warning in the library).
- The Hydra `bpm` global is synced with the scheduler.
- Audio reactivity uses Hydra's `a.fft` (`detectAudio: true`), shared with the audio analyzer.

### 6.2 textmode.js

- textmode.js + textmode.synth.js render into a dedicated canvas.
- The canvas is fed into Hydra via `sN.init({ src: canvas })` and used as `src(sN).out(o1|o2)`.
- Hydra-output-into-textmode (ASCII-fying Hydra visuals) is a future "composite clip" type (e.g. `engine: "textmode"` + `deps.hydraInput: true`).

### 6.3 ISF

- An ISF renderer runs in a dedicated canvas and is fed into Hydra like textmode.
- ISF JSON metadata (DESCRIPTION, CATEGORIES, INPUTS) is used directly for description / tags / params.
- INPUTS of type float / bool / color become controllable `params`; `audio` / `audioFFT` inputs are fed from the audio analyzer.
- Porting simple ISF shaders into Hydra via `setFunction` is a possible future option.

### 6.4 Source allocation (s0–s3)

- `s0`–`s3` are **managed by the playback engine**; clip code must not hard-code them.
- Example allocation: external-engine output of the current clip, of the next clip, camera, spare.
- Clips containing `s0.initCam()` etc. are abstracted at ingestion (placeholders such as `{{SRC_CAM}}`) and bound at runtime.

### 6.5 WebGL contexts

- Browsers limit the number of WebGL contexts. At most these exist at once: main Hydra + current external engine + next external engine.
- `prepare()` the next clip only once it is confirmed; `dispose()` the previous clip after the transition finishes.

## 7. Playback flow

```
[A playing on o1]
   │  Right after A starts: request candidates (§8) → show 3, set #1 as "Next"
   │  User clicks a candidate → replaces "Next"
   │  Once "Next" is set: prepare() B and preload it into o2 (not visible)
   ▼
[Transition starts] — one of:
   - A has used up its bars (auto-advance)
   - User presses "Go" (runs at the next bar)
   - User presses "Go now" (immediate)
   ▼
[o0 = transition(o1, o2, progress)]
   ▼
[Done] B is promoted to o1 (or buffer roles are swapped), A is disposed
```

- **All switches are quantized to the start of a bar** (except "Go now").
- Auto-advance can be toggled. When off, A keeps playing until "Go".
- **Hold**: extend the current clip (pause auto-advance).
- **Back**: return to the previous clip.
- **Panic**: blackout / freeze / safe clip (a pre-selected, always-fine clip).
- If the track has a next item, it is the initial "Next"; candidates are shown as alternatives. After the end of the track, the #1 candidate becomes the default.

## 8. Candidate generation

### 8.1 Pipeline

```
prompt / state
   │
   ├─ (1) Filter: commercial mode, unsupported isolated clips, missing deps (no camera…), last N clips
   ├─ (2) Embedding search: embed the prompt (or the current clip's description) with Workers AI,
   │       top K = 20 from Vectorize (filters applied as Vectorize metadata filters)
   ├─ (3) Decision provider: choose among the K clips, plus energy (score) and transition (choice)
   └─ (4) Return the top 3. #1 is the default "Next"
```

- The decision model only receives **the K candidates**, never the whole library.
- With an empty prompt, the query is built from the current clip + audio state + section.
- In local mode there is no Workers AI and no Vectorize, so step (2) is replaced by the neighbor table + tag dictionary (§8.5).

### 8.2 Decision input (state)

```jsonc
{
  "prompt": "darker, slower",                     // the standing direction's text (§8.6); may be Japanese
  "current": { "id": "...", "description": "...", "energy": 4, "engine": "hydra" },
  "history": [ /* last 5: id, engine, energy */ ],
  "audio": { "lowEnergy": 0.72, "highEnergy": 0.31, "trend": "rising", "bpm": 128 },
  "section": { "current": "build", "next": "peak" },   // if the track has sections
  "candidates": [ { "id": "...", "description": "...", "tags": [...], "energy": 3, "engine": "isf" } ]
}
```

Questions (all asked in one call):

- `choice`: which of the K clips fits best as the next clip
- `score`: how intense the visuals should be now (1–5)
- `choice`: which transition type fits

### 8.3 Using the results

- Probabilities are **used for ranking only, never as thresholds** (calibration differs between providers; e.g. Kev is reported to be less calibrated than Jev).
- Candidates are requested right after A starts, so results are always ready before the transition.
- A new prompt triggers an immediate re-request.
- Each candidate's `source` / `providerId` is shown subtly in the UI.

### 8.4 Decision providers

The decision layer is pluggable. **The default is Jev on Cloudflare Workers AI**; any number of additional providers can be configured in the settings screen and arranged in a fallback chain.

#### Provider kinds

| kind | Transport | Examples |
| --- | --- | --- |
| `cloudflare-ai` | `env.AI.run(model, { state, questions })` via the Worker's AI binding (optionally through an AI Gateway) | `typesafe/jev` (default) |
| `systemone-http` | `POST {baseUrl}/v1/systemone` with a `{ state, questions }` body (TypeSafe System One–compatible) | TypeSafe direct, Kev, other compatible servers, OpenRouter's System One–compatible endpoint |

Adding more kinds later (e.g. Vercel AI Gateway's evaluate interface) must only require a new client in `packages/decision`.

#### Configuration

```ts
interface DecisionProviderConfig {
  id: string // "cf-jev", "kev-local", ...
  label: string
  kind: 'cloudflare-ai' | 'systemone-http'
  enabled: boolean
  model: string // "typesafe/jev", "jev-latest", "kev-4b", ...
  baseUrl?: string // systemone-http only
  gatewayId?: string // cloudflare-ai only: route through this AI Gateway
  auth?: {
    type: 'none' | 'bearer' | 'header' | 'cf-access-service-token'
    secretRef: string // name of a Worker secret OR id of an encrypted secret in D1
    headerName?: string // for type "header"
  }
  timeoutMs: number // default 800
  maxCandidates: number // upper bound on K for this provider (context / option limits)
}

interface DecisionSettings {
  chain: string[] // ordered provider ids, e.g. ["cf-jev", "kev-local"]
  profiles: {
    // switchable in the live UI
    online: string[] // default: ["cf-jev"]
    local: string[] // default: ["kev-local"]
  }
  monthlyBudgetUsd?: number // optional soft cap; see cost tracking
}
```

- **Default configuration (seeded on first run):** one provider `cf-jev` (`cloudflare-ai`, model `typesafe/jev`), `chain = ["cf-jev"]`. No API keys are required.
- Behavior on failure: try providers in `chain` order; on timeout / error, move to the next one and log a `provider_fallback` event. If all fail, use the embedding ranking + rules; offline, use §8.5.
- A **response normalizer** per kind converts every provider's response into one internal shape (Cloudflare wraps results in an envelope; field names for probabilities/confidence may differ — verify each).
- Question-type names follow System One (`choice`, `score`, `noul`); clients map them if a provider uses other names.

#### Settings screen (`/studio/settings/decision`)

- List of providers: add / edit / enable / disable / delete, drag to reorder the chain.
- **Test button**: sends a fixed sample request, shows latency, the normalized answer, and raw response.
- Profile switch (online / local) is also available as a toggle on the live screen.
- Secrets:
  - Preferred: Worker secrets set with `wrangler secret put`; the config stores only the secret name.
  - For secrets added from the UI: stored in D1 encrypted with AES-GCM using the `SETTINGS_ENCRYPTION_KEY` Worker secret. **Secrets are never returned to the client** (the UI shows only "set / not set").
- Self-hosted providers reachable from the internet should be behind Cloudflare Tunnel + Access and use `cf-access-service-token` auth (sends `CF-Access-Client-Id` / `CF-Access-Client-Secret`).

#### Cost tracking

- Log input tokens (if reported) and latency per call in `session_events`.
- Jev is billed on input tokens only; with K = 20 a call is a few thousand tokens, so a 2-hour set costs cents. Still, show usage per session and warn when `monthlyBudgetUsd` is approached.
- `/api/candidates` requires owner auth and is rate-limited (Workers Rate Limiting binding).

### 8.5 Offline fallback (Worker unreachable)

The browser cannot embed prompts offline, so it uses two precomputed structures (downloaded into IndexedDB):

- **Neighbor table**: for each clip, its top 20 similar clips (from Vectorize, saved at ingestion). Candidates are the current clip's neighbors, ranked by energy / history / engine rules.
- **Tag dictionary**: words in prompts ("暗く"/"darker", "速く"/"faster", "文字"/"text"…) → tags / energy / palette.

These two structures are the one offline mechanism, and it runs in two places. The browser copy above is the fallback for a deployed Worker that becomes unreachable mid-show. In local mode (§15.3) the same structures live in the local D1 and the **local Worker** does the ranking — `packages/decision` is pure, so the same code runs unchanged in a Worker or in the browser — with the `local` decision profile (e.g. Kev on localhost) re-ranking the result.

### 8.6 Steering chat

The performer steers the decision model in words. A chat message becomes a **direction**: a standing instruction that keeps applying until it is replaced or cleared, where a one-shot prompt affected a single request. The chat is §8.2's prompt input grown up — there is no second input beside it.

**The chat steers; it never acts.** It changes which clips are offered and how they rank. It never starts a transition, holds, skips, or moves a parameter: those stay on the buttons and keys of §12.1, where a misread sentence cannot reach the output (§0, principle 1).

```ts
interface Direction {
  text: string // the performer's words; shown in the UI and sent as `prompt` (§8.2)
  tags?: string[] // prefer clips carrying these
  avoidTags?: string[]
  energyTarget?: 1 | 2 | 3 | 4 | 5
  energyTrend?: 'rise' | 'hold' | 'fall'
  palette?: string[]
  engine?: EngineKind
  ttlBars?: number // how long it stands; undefined = until replaced or cleared
  source: 'dictionary' | 'llm' | 'manual'
  at: number
}
```

- `text` reaches the decision provider as §8.2's `prompt`; the structured fields feed step (1) of §8.1 as filters and the transition rules of §9.2. The provider contract does not change.
- **Interpretation is a two-step chain, like the provider chain.** The tag dictionary (§8.5) runs first: it is instant, needs no network, and yields a usable direction on its own. When an interpretation provider is configured and reachable, an LLM then fills what the dictionary could not and replaces the direction with `source: "llm"`.
- **Interpretation is never on the playback path.** A direction applies to the _next_ candidate request. If the LLM is slow or fails, the dictionary's direction stands, nothing waits, and the show does not notice.
- Local mode runs the dictionary step only (§15.3).
- Every message and every direction change is logged (§16). What was asked for, and what the performer chose immediately afterwards, is the most valuable pair vev can record.

## 9. Transitions

### 9.1 Types (Hydra implementation sketch)

| type | Implementation | Good for |
| --- | --- | --- |
| cut | swap o1 ↔ o2 at a bar start | energy going up, drops |
| crossfade | `src(o1).blend(src(o2), () => p)` | default |
| modulate | `src(o1).modulate(noise(3), () => p).blend(src(o2), () => p)` | clips with a similar mood |
| feedbackMelt | keep o0 feedback while moving to B | moving into feedback-based clips |
| luma | `src(o1).layer(src(o2).luma(() => 1 - p))` | large brightness differences |
| diff | e.g. `src(o1).diff(src(o2).mult(solid(), () => p))` | breaks, glitchy moves |
| asciify | gradually turn A into characters when B is textmode | moving into textmode |

`p` is the progress 0→1 driven by the scheduler (easing applied).

### 9.2 Automatic selection (defaults)

Unless `TrackItem.transitionLocked` is true, choose in this order:

1. Explicit user choice → use it
2. Rules
   - Next section is `peak`, or energy +2 or more → `cut` (on the bar)
   - Next section is `break`, or energy −2 or more → `crossfade` over 4 bars
   - B `usesFeedback` → `cut` (the feedback creates a natural transition by itself)
   - Engine changes (hydra → textmode etc.) → `crossfade` 1–2 bars; into textmode → `asciify`
   - Same engine, energy difference within ±1 → `modulate` 1 bar
   - Large average-brightness difference → `luma`
3. The decision provider's `transition` answer (when rules don't decide, or as a weighted input)
4. `Track.defaultTransition`

- The automatically chosen transition is shown in the UI and can be changed with one click.
- If the same transition was used three times in a row, prefer a different one.

## 11. Clip ingestion

```
Input (pasted code / URL / ISF file)
  → Extract license info (header comments, ISF CREDIT); required at registration if missing
  → Normalize code
       - Hydra: abstract .out() targets and s0–s3, turn numeric params into macros
                (e.g. speed / modulation amount → () => intensity * original)
       - textmode: canvas and size provided from outside
       - ISF: unchanged (INPUTS → params)
  → Analyze dependencies (feedback / outputs / sources / audio / extensions) → isolated flag
  → Validation probe (§11.2's gate, run in the browser): exactly one .out() call, compiles,
       renders without errors, is not a black frame, holds its frame budget
       the "exactly one .out()" half is ALSO enforced by POST /api/clips, from the same
       scanner — the other four need a GPU and cannot be re-checked in a Worker
  → Thumbnail: render the clip in the registering user's browser and record a few seconds with
       canvas.captureStream + MediaRecorder → upload WebM to R2
       palette is sampled from THOSE FRAMES and uploaded with the recording — the rendered pixels
       are the ground truth, so no model is asked (ADR 0005)
  → Annotation (asynchronous, off the INGEST queue; never blocks the steps above):
       typed questions to typesafe/jev → tags (fixed vocabulary), energy, motion, density, layerHint
       one generative call → description (best effort: a failure leaves it empty)
       deps → the derived tags feedback and audio-reactive, never asked of a model
       ISF: use metadata first, the model fills only missing fields
  → Embedding (Workers AI → Vectorize), update the neighbor table (for offline use)
  → Human review screen → reviewed = true
```

- Lesson from the original article: still frames lead to wrong judgments about motion. **Estimate mainly from the code**; the thumbnail video is only a secondary signal.
- Unreviewed clips may appear as candidates, but are marked in the UI.
- **Registration works in local mode; annotation does not.** Registration itself needs only the browser (normalization, probe, thumbnail) plus D1 and R2, all of which have local implementations — the e2e seed driver registers clips through `POST /api/clips` against `pnpm live`, and M2's registration captures were taken the same way. Annotation needs Workers AI and Queues, which always reach the network (§15.3), so `INGEST` is simply absent locally and `POST /api/clips` logs the failed enqueue and returns the clip `annotationStatus: 'pending'` rather than failing a registration that succeeded. A clip registered at a venue therefore has no tags, no energy and no description until it is re-annotated online. **The library is still prepared before the show** — that is the operational rule; it is now a consequence of annotation, not of registration.

### 11.1 Where each step runs

| Step | Runs in | Why |
| --- | --- | --- |
| Normalization / dependency analysis | Browser (registration screen) and Worker, via `packages/ingest` | Instant preview on registration; re-validated on save |
| Validation probe / thumbnail recording / palette sampling | Browser (registration screen) | Needs WebGL; Workers cannot render. The palette is read out of the recorded frames (ADR 0005), so it reaches the server with the thumbnail, not with the annotation |
| Annotation (typed questions + description) | Queue consumer (Worker) | Slow, so async; updates the clip when done. Absent in local mode — see §11's local-mode note |
| Embeddings / neighbor table | Queue consumer (Worker) | Workers AI + Vectorize |

- The registration screen runs the clip for a few seconds; only clips that render without errors can be saved.

### 11.2 Room for generated clips

Generating clip code with a model is a later feature (§1), but a few MVP decisions would be expensive to reverse, so they are made now rather than assumed away:

- **Provenance is a field, not an inference.** `Clip.origin`, `derivedFrom` and `generator` exist from the first migration (§5). A generated clip has no author and no source URL, so the credit export (§14.2) and the commercial-use filter need a shape that says so instead of guessing from a blank `author`.
- **Ids are opaque, slugs are separate.** An id built out of an author's name cannot name a clip that has no author. Ids are stored in tracks, session logs and Vectorize, so this is the one field that cannot be changed later.
- **A generated clip is untrusted code**, whatever produced it, and reaches the show through the same sandbox third-party clips require (§13) — not through the owner-trust path.
- **The compositor takes a `TextureSource`** (§6), so an isolated or sandboxed renderer can be substituted without touching the compositor.
- **The validation gate is a reusable probe, not a screen.** "Compiles, renders without errors, is not a black frame, holds its frame budget" lives in `packages/ingest` and runs headlessly, because generation needs it automatically and in bulk. Building it inside the registration UI would mean writing it twice.
- **Generation never touches the playback path**, exactly as chat interpretation does not (§8.6): a generated clip enters the top of the §11 pipeline like any other, and becomes a candidate only once it has passed it.
- **Safe defaults**: a generated clip starts `reviewed: false` and `commercialOk: false`. Nothing about who owns model output is settled (§17), and defaulting the other way would silently put unclearable material into a commercial set.

## 13. Public URLs, permissions, security

- Authentication uses Cloudflare Access.
  - Protected: `/studio/*` (live, library, editor, settings) and all write `/api/*` routes, plus `/api/candidates` and `/api/settings/*`.
  - The Worker also verifies `Cf-Access-Jwt-Assertion` (defense in depth against Access misconfiguration).
  - Public: `/t/<slug>` (viewing) and `GET /api/public/tracks/:slug`.
- Tracks can be published at `/t/<slug>` (private / unlisted / public). Public track JSON is cached in KV.
  - Viewers: play the track (auto-advance in track order; no decision calls) and see credits.
  - Owner: edit, live mode (candidates and decision providers).
- **Clip code is evaluated**, so only clips from the trusted library may run.
  - In the MVP only the owner can register clips.
  - Accepting third-party clips requires review plus execution in a sandboxed iframe on a separate origin (redesign needed).
  - Model-generated clips (§11.2) are third-party code for this purpose and take the same path; being generated locally makes code no more trustworthy.
  - CSP is set with Hono's `secureHeaders` middleware; external scripts are allow-listed (extensions loaded via `loadScript` use an allow list).
  - Public pages only run code of clips referenced by the track, fetched from the library.
- **Local mode has no Cloudflare Access.** The Worker binds to `127.0.0.1` only, and a request that does not come from loopback is never treated as the owner. Local mode is never served on a LAN address or `0.0.0.0` (§15.3).
- Chat text leaves the Worker only for the configured interpretation provider (§8.6), on the same owner-only, rate-limited path as `/api/candidates`. In local mode nothing leaves the machine.
- **A preview deployment is a second front door.** Cloudflare Access policies bind to hostnames, so a policy covering the custom domain does not cover a `*.workers.dev` preview or version URL: publishing one exposes `/studio/*` and the owner `/api/*` routes to anyone holding the link. A reachable deployment is only acceptable when its hostname is covered by the Access policy, or when it carries no owner routes at all. The same applies to bindings — a preview version runs against whatever environment it was uploaded with, so a preview wired to production bindings can write to production data. Previews therefore take their own environment, never the production one.
- Decision-provider secrets never leave the Worker (§8.4).

## 15. Performance and operations

### 15.1 Self-hosting

- vev is not offered as a shared hosted service; each user deploys to their own Cloudflare account (their own costs, data, and decision-provider usage).
- `pnpm setup` (interactive) does: `wrangler login` check → create D1 / R2 / KV / Vectorize index / Queue → write IDs into `wrangler.toml` → run D1 migrations → set secrets (`SETTINGS_ENCRYPTION_KEY`, optional LLM key) → seed the default decision provider (`cf-jev`) → print the Cloudflare Access setup steps.
- README includes a "Deploy to Cloudflare" button if the required bindings are supported by it; otherwise `pnpm setup` is the documented path.
- Requirements: Cloudflare Workers Paid plan is recommended (Workers AI / Vectorize / Queues usage); document what works on the free plan.
- Upgrades: D1 migrations are versioned; `pnpm migrate` is safe to run repeatedly.

### 15.2 Runtime

- Target: 1080p / 60 fps on an Apple Silicon MacBook. Lower internal resolution for weaker machines (Hydra `setResolution`, textmode grid size).
- Stop render loops of hidden engines. Candidates use thumbnail videos only.
- **Local mode** (`pnpm live`): the show runs on the performer's own machine with no internet. See §15.3.
- **Fallbacks**: provider chain → embedding ranking + rules → neighbor table + tag dictionary in the browser → track order → random (excluding recent). Playback never stops.
- Service Worker caches the library and thumbnails; an "Prepare offline" button downloads all clips, thumbnails, and neighbor data needed for a track before a show.
- Session logs are written to IndexedDB and sent to D1 in batches when online (`/api/sessions/:id/events`).

### 15.3 Local mode (running at a venue)

Local mode is how vev runs at a venue: the same artifact as the deployed one — the built SPA served by the built Worker — hosted by a local workerd on the performer's machine, with local D1 / R2 / KV and no internet. `pnpm live` starts it. `pnpm dev` is for development only: **a dev server never plays a show**, because what plays must be what was built and tested.

- **The host process must be inert**: no file watching, no rebuild on change, a fixed port, a persistent state directory, no telemetry, and no login or network access at startup. Candidates: `wrangler dev` (simplest, if watching and telemetry can be turned off), Miniflare's programmatic API driven by a small script (owns the port, the persistence directory and the lifecycle), or raw `workerd` with a generated config. Decided in M11 (§17).
- **The first run is not at the venue.** `pnpm live` needs downloads (the workerd binary, dependencies) and a build. It fails with a clear message when the build or the local state is missing, rather than reaching for the network while the doors are open.
- **Cloud-only bindings are absent.** Workers AI (embeddings, Jev) and Vectorize have no local equivalent, and ingestion Queues are pointless without them. Every route works with `AI`, `VECTORIZE` and the queue producer absent: candidate generation skips §8.1 step (2) and the local Worker ranks the neighbor table + tag dictionary (§8.5) instead; clip registration is unavailable (§11).
- **The steering chat runs dictionary-only** (§8.6): no interpretation provider is reachable, so a direction comes from the tag dictionary alone and the UI says so. Nothing else about the chat changes.
- **The decision profile comes from the environment**, not the live toggle: local mode starts on the `local` profile, so the chain never begins with a provider that needs the internet. A local Kev shares one machine's GPU with 1080p60 rendering (§17).
- **Auth**: the invariant is in §13. `SETTINGS_ENCRYPTION_KEY` must exist locally (`.dev.vars`), or provider secrets copied by `sync:pull` cannot be decrypted.
- **Secure context**: `http://localhost` is a secure context, so `getUserMedia`, the Service Worker and `BroadcastChannel` work without TLS. A LAN address is not, so control and output windows stay on the one machine — which §3 requires anyway.
- **Before the show**: `pnpm sync:pull` copies the deployed D1 / R2 data into the local state, and "Prepare offline" (§15.2) fills the browser caches for the track.
- **After the show**: `pnpm sync:push` sends the locally recorded session events to the deployed D1; without it local sessions never reach the dataset in §16.

- [x] Whether oxlint reports anything inside `.svelte` files, and whether `svelte-check` is therefore needed in `pnpm check` — **answered in M0**: oxlint lints a `.svelte` file's `<script>` block with its syntactic rules only — confirmed directly (`func-style`, `consistent-type-specifier-style` and `unicorn/catch-error-name` all fired inside `apps/web/src/routes/+page.svelte`'s script block). It does not lint template markup at all, which [oxc's own compatibility documentation](https://oxc.rs/compatibility.html) states plainly ("No template linting yet" for Svelte and the other frameworks it lists); and it does not run type-aware rules against `.svelte` script contents either — confirmed by injecting an unused variable into a script block, which `pnpm check` did not report. `svelte-check` is the tool that would cover both gaps, and it cannot run in this repository yet — see ADR 0001 for why. `.svelte` templates are therefore outside `pnpm check`'s type and lint gate; `AGENTS.md` and `CONTRIBUTING.md` both state this as a rule (keep components thin) rather than only as a known gap.
- [x] Whether wrangler's named environments (`env.local`) inherit every top-level key — **answered in M0, verified**: `assets` IS inherited by a named environment from the top level; `vars` and `d1_databases` are NOT — removing either block from `env.local` while it stayed at the top level made wrangler print a startup warning that it is not inherited and dropped the corresponding binding (`vars` disappeared from the bindings table; removing `d1_databases` dropped `DB` and made `/api/health` return 500). `apps/api/wrangler.jsonc`'s `env.local` block repeats `vars` and `d1_databases` but not `assets`, and its comment states this asymmetry; a future addition of a new top-level key must re-verify inheritance rather than assume it one way or the other.
- [ ] **The probe's frame-budget threshold is unmeasured on real hardware.** `FRAME_BUDGET_MS` in `packages/engines/src/hydra/probe.ts` is 50ms per probed tick — chosen as roughly three missed frames at 60fps, pathological but clear of ordinary jitter. The gate can now genuinely fail: until the fix in `54b326d` the loop timed `compositor.tick()` alone, which only queues regl draw calls, so a driver could accept an expensive frame near-instantly and the check was structurally incapable of rejecting anything; it now calls `readSlotPixels` once per tick purely as a GPU synchronisation point, and the number it reports is a real render cost. What is NOT known is whether 50 is the right number, because the only figures that exist come from SwiftShader — the software rasteriser Chromium falls back to in the headless e2e drivers. The two M2 clips measured 9.7ms (`quiet`) and 18.6ms (`loud`) there (`artifacts/2026-09-29-m2/register-results.json`, a gitignored local capture). Those are _software_ numbers, an order of magnitude off a performer's GPU, and the threshold was deliberately NOT tuned against them: tightening 50 until `loud` sat comfortably under it would calibrate the gate to the slowest renderer vev will ever run on, and would start refusing clips that a real projector plays effortlessly. What would settle it: run the probe on the machine that will actually perform, on a dozen clips spanning trivial to deliberately expensive, and set the threshold from that distribution — and record the GPU it was measured on, because the number is only meaningful with it.
- [ ] **A clip that writes more than one buffer is refused, not remapped.** §6.1 gives the compositor all four Hydra buffers — `o0` is the final output, `o1` and `o2` are the two clip slots, `o3` is the compositor's spare — so a clip owns exactly one, whichever slot it is loaded into. `rewriteOut` (`packages/engines/src/hydra/rewrite.ts`) rewrites a clip's single `.out(...)` call, bare or named, to that slot's buffer; `probeClip` refuses anything with two or more `.out(` calls up front, before mounting anything, with `reason: 'multi-output'` and a message the registrant can act on, and `POST /api/clips` makes the same refusal with the same message from the same scanner — it is the one half of §11.2's gate that needs no GPU, so it is the one half the store can enforce for itself. That is a deliberate refusal, not an oversight: with two outputs there is no way to tell which one the author meant to be the clip, and guessing would write a buffer the clip does not own. What is NOT known is how common such sketches are in the wild, or whether the multi-pass ones worth having can be remapped rather than rejected — compositing a clip's own extra buffers inside its slot, which would mean giving each slot a private buffer set instead of a single `oN`. That is the unimplemented alternative, and it is a compositor change, not a rewriter change. What would settle it: count how many of the 20 clips the author actually wants are refused for this reason. If the answer is none, the refusal is correct forever; if it is several, the compositor redesign has a price attached to it.
- [ ] **`src(oN)` reads are not remapped either, and nothing fails when they are wrong.** This is the more insidious half of the buffer question. `rewriteOut` rewrites `.out(...)` targets only; it never touches a `src(o0)` on the reading side. So a feedback sketch written as `src(o0).modulate(...).out(o0)` becomes `src(o0).modulate(...).out(o1)` when it is loaded into slot `a`: it now _writes_ its own slot correctly and _reads_ `o0`, which is the compositor's final mixed output — the blend of both slots, including itself one frame late. It compiles, it renders something, it is not a black frame, it holds the budget, and it passes the probe looking nothing like what its author intended. Nothing in the pipeline can tell the difference, because "renders something plausible" is exactly what the gate tests for. Two related facts: `analyzeHydra` does flag it (`deps.usesFeedback`, surfaced as the derived `feedback` tag), but that flag is recorded, not acted on — nothing at playback reads it; and its detector, `FEEDBACK_RE`, matches `src(o0)` ONLY, so a sketch that fed back through `src(o1)` would not even be flagged. `isolated` is computed from the same `.out(` count the multi-output refusal uses, and both the browser probe and `POST /api/clips` refuse a clip with more than one call — so it is `false` for every clip that reaches the library, and the escape hatch §5 describes exists in the type and is never set. That conclusion held before M2's final review only by accident, and this entry used to give the wrong reason for it: until then the refusal ran in the browser alone (the route accepted a two-`.out(` clip with a 201) and `analyzeHydra` counted calls with a regex of its own over raw source, so a clip with a commented-out `.out(` line passed the probe and was stored `isolated: true` anyway. Both are fixed — one scanner answers the question and the server enforces the answer — so the conclusion is now true for a reason a later milestone can lean on. What would settle it: rewrite `src(oN)` reads to the clip's own slot buffer alongside the `.out()` rewrite, and prove it with a feedback clip whose trail is visibly its own image rather than the mix; or, failing that, refuse feedback clips outright the way multi-output ones are refused, so the failure is visible instead of pretty.
- [ ] **`TAG_THRESHOLD` and the size of the tag vocabulary are both unmeasured guesses.** The threshold is 0.6 and the vocabulary holds eighteen tags (`apps/api/src/ingest/tags.ts`), plus the two derived from `deps`. Neither number has been tuned against a real library, for the plain reason that no clip has ever been annotated (see the credits item below). The threshold is exported and the tests assert _relative_ to it — `TAG_THRESHOLD + 0.01` is tagged, `TAG_THRESHOLD - 0.01` is not — so the first tuning pass moves one number and breaks nothing. What is NOT known: whether 0.6 over-tags (every clip comes back "organic" and "gradient", making the filter useless) or under-tags (most clips come back with an empty array), and whether eighteen statements cover what a real library contains. The structural cost is recorded in ADR 0005 and does not go away with tuning: a fixed vocabulary cannot describe a clip nobody anticipated, and widening it later means re-annotating every clip already stored, because the new question has no answer for them. What would settle the threshold: annotate the first 20 clips, print every tag's probability rather than its verdict, and pick the cut from that distribution. What would settle the vocabulary: read those same 20 clips' tag sets and count how many came back empty or wrong.
- [ ] **jev's wire format is unconfirmed, and the blocker is an account, not the code.** `typesafe/jev` is a third-party model billed from **prepaid AI Gateway credits**, not from Workers Paid neurons, and this account holds none. The call is rejected with `AiGatewayError: 2021: Insufficient AI Gateway credits` — and, critically, **before the request is validated**, so the rejection says nothing at all about whether the payload was right. Every request and response shape in `apps/api/src/ingest/jev.ts` therefore comes from Cloudflare's model page (read 2026-09-29) and has never been seen on the wire. What IS confirmed: the `AI` binding reaches the gateway, the model id `typesafe/jev` is routed (a wrong id returns a _different_ error — the rejection above is specific to this model being resolved and then refused on billing), and `@cf/` models on the same account, including `@cf/qwen/qwen2.5-coder-32b-instruct`, answer normally. The `wrangler ai models` omission is not evidence of anything (see above). The exposure is bounded by design: every jev shape assumption is confined to that one module, so a wrong shape costs one file and no schema, no route and no stored row. **The unblocking step is to load credits in the Cloudflare dashboard under AI Gateway**, then register one clip and watch its `annotationStatus` move `pending → ok`. That single call either confirms `jev.ts` or rewrites it. Two shape assumptions to check first, both spelled out in that file's header: the response envelope may carry siblings such as `usage` next to the answers (the parser already tolerates them), and `confidence` is parsed as optional even though it is documented as present.
- [ ] **`ownerId` is hard-coded, because identity is unanswered.** §13 assumes a single owner and Cloudflare Access decides only _whether_ a request is that owner, never _which_ — so `apps/api/src/routes/tracks.ts` sets `OWNER_ID = 'owner'` on every track it creates rather than deriving identity from the Access assertion. That is the honest choice today: `apps/api/src/access.ts` only checks the assertion is _present_, so anything derived from it would be a guess dressed as a fact. Two places move the day a second owner exists — that constant, and the access guard, which would have to decode and verify the assertion to name anyone. A third thing is simply missing: the `clips` table has no owner column at all, so clips are not merely single-owner, they are unowned. What would settle it: full Access JWT verification (fetch and cache the team's JWKS from `ACCESS_TEAM_DOMAIN`, check signature, issuer, audience and expiry against `ACCESS_AUD` — both vars are already wired), then a decision about whether clips are a shared library or per-owner, which is a migration either way.
- [ ] **The browser drivers are deliberately outside `pnpm test` and CI, and their visual evidence is not an assertion.** `apps/web/e2e/` holds Playwright drivers for the library, the track editor and the control panel; running them found two real defects no unit test had. They are not in the automated gate on purpose — they need a running `pnpm live` and, on a fresh machine, a few-hundred-megabyte Chromium download, and Playwright is not a dependency of this repository (`npx --package` supplies it for the life of the command). The cost is that nothing re-runs them: a regression in the `$effect` that refetches on a filter change, or in a fade refusal reaching the screen, is caught only when a human remembers to run the drivers. Worse, one of the things they were written to show cannot be asserted at all: `gl.readPixels` on the output canvas returns all zeros because the context is created with `preserveDrawingBuffer: false`, so the crossfade captures are screenshots a human has to look at, not a comparison a script can fail on. And SwiftShader means nothing they measure speaks to frame rate on a projector (see the frame-budget item). What would settle it: either a CI job that installs Chromium and runs them (paying the download, accepting the software-rendering caveat), or an output-window build flag that turns `preserveDrawingBuffer` on under test so a blend can actually be asserted.
- [ ] **The Cloudflare Access guard has never been round-tripped.** `requireAccessAssertion` is unit-tested in `apps/api/test/access.test.ts` against synthetic headers, and that is the whole of its evidence. It has not been exercised against real Access: local mode has none by design (§15.3, and the guard disables itself when `VEV_MODE === 'local'`), and the deployed preview — which _is_ behind Access as of M2 — has not been driven through a login and out the other side. So the pair "Access's edge allows the request" and "the Worker sees a non-blank `Cf-Access-Jwt-Assertion` on it" is assumed, not observed. Related and still absent: there is no Access **bypass policy for `/api/health`**. The Worker names `/api/health` as its only public path, but Access intercepts at the edge first, so the deployed preview's health endpoint redirects to the login page and cannot be curled — which is why CI is not pointed at it and why checking a promoted version's `commit` means opening a browser. What would settle both: a manual browser round trip through Access to `/studio`, confirming an owner route answers and recording what the Worker saw; and an Access bypass (or service-token) policy scoped to `/api/health` alone, then `curl` against it from outside.
- [ ] **A clip registered without a thumbnail has no palette, and there is no way to add one afterwards.** `palette` is sampled from the frames the thumbnail recording actually rendered and is uploaded with that recording (`POST /api/clips/:id/thumbnail?palette=...`), which is what makes it ground truth rather than a guess (ADR 0005). The consequence is that the two travel together: skip the recording and the row has neither. The endpoint itself is not the obstacle — it is a normal route and takes a recording for any already-registered clip — but nothing in the UI reaches it outside the registration sequence, so in practice the only way to give an existing clip a palette is to register the clip again. What would settle it: a library action that re-runs the recording for an existing clip against the same endpoint. Until then, anything reading `palette` must handle its absence, and a clip with no thumbnail is a clip the library cannot show a colour for.
- [ ] **Three things M2 produces with no consumer in M2: `derivedFrom`, five annotated fields, and one flag's advice.** Recorded together because they are one shape: something the milestone produces that nothing in the milestone reads or offers. (a) `derivedFrom` has a column, a `nullsToUndefined` entry and a schema field, is absent from both the registration and the patch schema, and has no writer anywhere — §5 describes it as the provenance link between a clip and the one it was derived from, which nothing yet creates. (b) Five of the seven annotated fields — `description`, `motion`, `density`, `layerHint` and `palette` — reach no screen: `clipSummarySchema` carries none of them and no `.svelte` file in the repository mentions any, so only `energy` and `tags` are visible. Defensible, since the five are M3's decision-engine inputs, but it means the annotator's output cannot be checked by looking at the app — which matters more than usual given that no annotation has ever actually run (see the credits item above). (c) The `annotation-failed` flag's detail reads "Re-run it, or fill the fields in by hand", and M2 implements neither: `enqueueAnnotation` has exactly one caller (registration) and nothing in the web app issues a clip PATCH. The flag's tone distinction — attention versus waiting — is right and worth keeping; it is the advice that names actions nobody can take. What would settle all three is the same milestone: M3's review queue gives `reviewed` its writer, gives a person somewhere to see and correct the annotated fields, and is the natural home for a re-annotate action. Until it exists, the flag should say what M2 actually offers.
- [ ] **Both annotation timeouts are guesses.** `JEV_TIMEOUT_MS` is 30s and `DESCRIPTION_TIMEOUT_MS` is 20s (`apps/api/src/ingest/annotate.ts`). They exist for a real reason — a call that never resolves is the one failure mode that does NOT end in `annotationStatus: 'failed'`: the consumer never acks, the queue redelivers until `max_retries` is spent, and the clip is silently left `pending`, a state nothing in the UI distinguishes from "annotation hasn't run yet". Whether Workers AI caps a hung call server-side is undocumented, and a defence resting on someone else's undocumented timeout is not a defence. But the _numbers_ are picked to be an order of magnitude above the only inference ever observed on this account (the `@cf/qwen` probe answered in well under a second) while keeping the worst case — two attempts, each a jev call plus a description call — near 100 seconds, comfortably inside a queue consumer's budget. No jev call has ever completed, so its 30s is bounded by nothing measured at all. What would settle them: log the observed duration of every annotation call once credits land, and set each timeout from the observed tail rather than from an order-of-magnitude guess.
