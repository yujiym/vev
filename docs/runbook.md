# Runbook

How to run vev locally and what bites. The design lives in [spec.md](./spec.md); decisions live in [adr/](./adr/README.md). This file is only what someone needs to operate the repository, and every entry was established by running it.

## Commands

| Command | What it does |
| --- | --- |
| `pnpm install --frozen-lockfile` | Installs; pnpm provisions Node itself. Has an `apps/web` `prepare` script (`svelte-kit sync`), but pnpm skips lifecycle scripts when install finds nothing to change — verified by moving `.svelte-kit` aside and running install both plain and with `--force`: neither regenerated it. It may still run on a genuinely fresh clone (untested); `pnpm --filter web run prepare` is the step that reliably regenerates it, which is why CI runs it explicitly, right after install. |
| `pnpm dev` | Development: the SPA on `127.0.0.1:5173` with `/api` proxied to the Worker on `127.0.0.1:8787`. Applies local D1 migrations first. |
| `pnpm live` | Local mode (§15.3): builds the SPA, applies local D1 migrations, and serves both from the Worker on `127.0.0.1:8787` — the same shape that deploys. |
| `pnpm check` | Typecheck, lint (oxlint) and format (oxfmt). |
| `pnpm test` | Every package's tests; `apps/api`'s run inside workerd. |
| `pnpm licenses:check` | Fails on a production dependency whose licence is not AGPL-3.0 compatible (§14.1). |
| `bash scripts/smoke-live.sh` | Starts `pnpm live` and asserts the single-origin contract: `/api/health` JSON, SPA fallback on an unmatched path, `404` on an unknown API route. CI runs this. |
| `pnpm deploy:preview` | Builds the SPA, then uploads a new Worker Version to the `preview` environment (a real screen, not localhost) and prints its Version ID — no URL, since M2 turned `preview_urls` off (see the one-URL gotcha below). Does not touch triggers (routes, `workers_dev`) or the stable custom domain — wrangler says so explicitly ("Changes to triggers ... must be applied with `wrangler triggers deploy`"). |
| `wrangler versions deploy --version-id <id> --percentage 100 --env preview -y` (run from `apps/api`) | Points `vev-preview.0x7.sh` (the only surviving preview URL) at a version `deploy:preview` already uploaded. `<id>` comes from `wrangler versions list --env preview` (newest first). `-y` skips the interactive prompt; without it the command asks which version(s) and what split, which cannot be answered non-interactively. |
| `pnpm --filter api run migrate:preview` | Applies D1 migrations to `vev-preview`, the preview environment's own remote database — never the `vev` production database. |
| `wrangler deployments status --env preview` (run from `apps/api`) | Shows which version is actually promoted (and at what percentage) on the stable preview deployment right now — `wrangler versions list --env preview` only lists versions that exist, not which one is live. |

## Gotchas

- **During `pnpm dev`, port 8787 serves a placeholder, not the app.** The Worker needs an assets directory to start, and in development the real SPA is Vite's on 5173. `apps/api/dev-assets/index.html` says so on the page itself. Only `pnpm live` serves the real build from the Worker.
- **After a change to the `miniflare` / `workerd` overrides in `pnpm-workspace.yaml`, reinstall from scratch.** A stale symlink survives in an already-installed `node_modules`; neither `pnpm install` nor `pnpm install --force` clears it. `rm -rf node_modules && pnpm install` does. A fresh clone and CI are unaffected — the lockfile is correct.
- **`pnpm migrate:local` does not pass `--env local`.** It works because the top-level and `env.local` `d1_databases` blocks are identical. If they ever diverge, this command will silently migrate the wrong database.
- **Name the next migration**: `drizzle-kit generate --name <name>`. Without it drizzle-kit invents a name and the file has to be renamed and its entry in `migrations/meta/_journal.json` corrected by hand.
- **`TEST_MIGRATIONS` is a required member of the global `Cloudflare.Env`** (`apps/api/test/env.d.ts`), and `apps/api/tsconfig.json` compiles `src` and `test` as one program. Inert while production code reads bindings through Hono's typed `Env`; revisit if any code adopts `import { env } from 'cloudflare:workers'`.
- **`.svelte` templates are outside the gate.** `pnpm check` reaches a component's `<script>` block with syntactic rules only — no template linting, no type-aware rules — because `svelte-check` cannot run against TypeScript 7 (see [ADR 0001](./adr/0001-vite-plus-toolchain.md)). Keep logic in `.ts` and components thin.
- **The M2 screens have browser drivers, and they are manual on purpose** — `apps/web/e2e/`, with its own README. They open `/studio/clips`, the track editor and the control panel in a real Chromium and assert on what is rendered, which is the half `vp build` cannot see: the `$effect` that refetches on a filter change, the refused-filter message, the reorder that has to survive a reload, the §14.2 refusal reaching the screen, and — the property that has diverged from the reducer twice — the fade refusals being VISIBLE on the panel. Running them found two defects no unit test had. Start `pnpm live` first (they need the app and the API on one origin, and they seed their own fixtures into the local D1), then `npx --yes --package playwright@1.63.0 node apps/web/e2e/<script>.mjs`. **If a driver misbehaves, look for an orphaned `workerd` before blaming it**: `wrangler dev` leaves children behind when killed abruptly, and one holding `:8787` makes the next `pnpm live` die on bind (so the drivers hit the old Worker and a possibly stale build), while one holding an open handle on `apps/api/.wrangler/state` keeps the OLD database alive after that directory has been renamed — a rename does not close a file handle. `pgrep -af 'wrangler|workerd'`, then `pkill -f workerd; pkill -f wrangler`, and check `:8787` is free before restarting. `playwright` is deliberately NOT a dependency — `npx --package` supplies it for the life of the command, and `apps/web/e2e/**` is excluded from lint in the root `vite.config.ts` for exactly that reason. **They are not in `pnpm test` and not in CI**: they need a running server and, on a fresh machine, a few-hundred-MB Chromium download (`npx --yes --package playwright@1.63.0 playwright install chromium` if a run reports the executable is missing). Two things they do not prove: SwiftShader is a software rasteriser, so nothing there speaks to frame rate on a real projector; and `gl.readPixels` on the output canvas reads all zeros (`preserveDrawingBuffer: false`), so the crossfade captures are evidence a human has to look at, not assertions the script can fail on.
- **Wrangler's named environments inherit `assets` but not `vars`, `d1_databases`, `r2_buckets` or `queues.producers`/`queues.consumers`**, so those are repeated under `env.local` (and `env.preview`) in `apps/api/wrangler.jsonc` wherever that environment needs them. Verified by removing each block and watching the binding disappear. `env.local` gets `r2_buckets` (`MEDIA` is a required binding and R2 works locally) but not `queues` (`INGEST` is optional; a queue is pointless offline, §15.3).
- **As of M2, `vev-preview.0x7.sh` sits behind Cloudflare Access, and `vev-preview.host3.workers.dev` no longer serves the app at all.** M1's "no Access yet, on purpose" state is over: Access binds to hostnames in the zone, so it protects the custom domain but can never protect a `*.workers.dev` hostname — the fix was to close that door instead (`env.preview.workers_dev` and `env.preview.preview_urls` are both `false` in `apps/api/wrangler.jsonc`). Requesting `vev-preview.host3.workers.dev` now returns Cloudflare's `error code: 1042` — the same signature the routes gotcha below describes, except this time it's deliberate. **This also means `/api/health` on the deployed preview now redirects to the Access login** (a browser-authenticated, manual check), and per-version `workers.dev` preview URLs (what `versions upload` used to print) no longer exist — the only surviving preview URL is the custom domain, and only a promoted version (`wrangler deploy` / `wrangler versions deploy`) is visible on it. `bash scripts/smoke-live.sh` is unaffected: it tests `pnpm live` (`--env local`, no Access), and CI is deliberately not changed to authenticate against Access.
- **The Worker also verifies `Cf-Access-Jwt-Assertion` itself (`apps/api/src/access.ts`), as defence in depth against Access being misconfigured off (§13) — but only as a PRESENCE check, not full verification.** It refuses (403) any request past `/api/health` that lacks a non-blank `Cf-Access-Jwt-Assertion` header; it does not decode the token or check its signature, issuer, audience or expiry. Full JWT verification (fetch and cache the team's JWKS from `ACCESS_TEAM_DOMAIN`, verify against `ACCESS_AUD`) was scoped as a stretch for the task that added this and did not land cleanly — two blockers, not code quality: (1) there was no way to obtain a real signed Access JWT to test against, short of driving a browser through Access's login flow, and (2) `curl` never reaches the Worker on the deployed preview to exercise it end-to-end, since Access's own edge redirect (302) happens before the request. Both `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` are already in `apps/api/wrangler.jsonc`'s `vars` (top level and `env.preview`) for whoever picks the stretch back up. **`ACCESS_TEAM_DOMAIN` is confirmed**: `https://vev-preview.0x7.sh/.well-known/cloudflare-access-protected-resource/studio` (unauthenticated) returns it directly as `team_domain`. **`ACCESS_AUD` is NOT independently confirmed** — it is the `kid` query param on the Access login redirect (`https://vev-preview.0x7.sh/studio` → `.../cdn-cgi/access/login/...?kid=<this value>`), which is very likely the application's audience tag but was not cross-checked against the Cloudflare dashboard, which is the actual source of truth. Verify it there before the stretch relies on it. The check is disabled whenever `VEV_MODE === 'local'` (local mode has no Access by design, §15.3) — **but the `apps/api` test pool's `VEV_MODE` is `'cloud'`, not `'local'`, despite `vite.config.ts` pointing `wrangler.environment` at `'local'` for D1/migrations** (`vite.config.ts`'s `miniflare.bindings` explicitly overrides `VEV_MODE` to `'cloud'`, the same way it overrides `GIT_COMMIT`). So the guard runs enabled in every `apps/api` test: any owner route Task 3 adds needs a real (non-blank) `Cf-Access-Jwt-Assertion` header in its test requests, or it 403s — do not "temporarily" disable the guard to make a red test pass.
- **The Worker's `env.preview` never points at the `vev` (production) D1 database** — it has its own `vev-preview` database (`bcee626b-7dbd-4456-8fb9-a708583e6e1d`), separate from `vev` (`6554a370-8884-4cbb-9f87-9d891a34ddcd`, reserved for M12). This is the whole reason the preview has its own `d1_databases` block instead of sharing the top-level one.
- **The Worker script has to exist before `versions upload` will work.** For a brand-new named environment, `wrangler versions upload --env preview` fails outright with "You cannot upload a new version of a Worker that does not yet exist. Please run the `deploy` command first." — there is no way around this with flags; a real `wrangler deploy --env preview` has to run once to create the script. (Before M2 this also created the `workers.dev` route; M2 turned that off — see the Access gotcha above.) This is a one-time bootstrap per environment (already done for `preview`); the repeatable `deploy:preview` script never needs to run it again.
- **Only one preview URL exists now: `vev-preview.0x7.sh`.** Before M2 there were two — a per-version `workers.dev` URL that `versions upload` printed fresh every run, and the stable `vev-preview.<subdomain>.workers.dev`/custom-domain URL that only a promotion moved. M2 set `env.preview.workers_dev` and `env.preview.preview_urls` to `false` (see the Access gotcha above), so per-version `workers.dev` URLs no longer print at all and the stable `workers.dev` hostname no longer resolves to the app (`error code: 1042`). `pnpm deploy:preview` (`versions upload`) uploads a version and prints only its Version ID — `wrangler versions list --env preview` lists uploaded versions but not which is live; `wrangler deployments status --env preview` (see the command table) is what shows the promoted version and its percentage, or check `/api/health`'s `commit` field once promoted (through a browser: it's behind Access now too). Promote with `wrangler versions deploy` (see the command table) to move `vev-preview.0x7.sh` to a new version; `deploy:preview` alone never does.
- **Adding `routes` to an environment silently disables `workers_dev` and `preview_urls` on the next triggers-changing deploy, unless you set them explicitly.** M1 verified this by accident (`workers_dev`/`preview_urls` defaulted to `false`, breaking `vev-preview.host3.workers.dev` with `error code: 1042`, until both were set back to `true`); M2 sets both to `false` on purpose, for the reason in the Access gotcha above — see there for the current, deliberate state.
- **`vev.0x7.sh` (no `-preview`) is deliberately not attached to anything.** That hostname is the production name; the production Worker does not exist yet (M12). Attaching it now would stand up a second Worker serving this same code against the production `vev` D1 database — exactly the duplication the separate `preview` environment exists to prevent.
- **`wrangler deploy --env preview` reported the `INGEST` queue's consumer trigger as failed, even though the deploy otherwise succeeded — because the Worker exported no `queue()` handler yet. It does now (M2); this should be gone, but has not been re-checked.** Verified while closing the workers.dev door for M2: `wrangler deploy --env preview` printed `Trigger configuration for "vev-preview" was only partially updated` with `Queue handler is missing` (code 11001) for the `INGEST` consumer, because no code in `apps/api/src` exports one yet. The Worker itself, its assets, the custom domain, the queue _producer_, and `workers_dev`/`preview_urls` all deployed fine regardless — wrangler says explicitly "Successful trigger changes were not rolled back." `wrangler versions upload` (`pnpm deploy:preview`) is unaffected: verified separately, it doesn't touch triggers at all (wrangler prints "Changes to triggers ... must be applied with `wrangler triggers deploy`"), so this only showed up on `deploy --env preview` or `wrangler triggers deploy --env preview`. The consumer handler has since landed, so the next triggers-changing deploy is expected to succeed cleanly — nobody has run one to confirm it (see "Not wired yet").

- **Annotation cannot run on this account: `typesafe/jev` needs prepaid AI Gateway credits and there are none.** Registering a clip enqueues annotation, the consumer calls `env.AI.run('typesafe/jev', ...)`, and the call comes back `AiGatewayError: 2021: Insufficient AI Gateway credits`. It is rejected **before the request is validated**, so the error says nothing about whether the payload was right — which is why `apps/api/src/ingest/jev.ts`'s documented request and response shapes are still unconfirmed (spec §17). This is billing, not configuration: jev is a third-party model billed from prepaid AI Gateway credits rather than from Workers Paid neurons, and `@cf/` models on the same account (including `@cf/qwen/qwen2.5-coder-32b-instruct`, which writes `description`) answer normally. **Do not read anything into `wrangler ai models` not listing it** — that command lists only the `@cf/` namespace and never shows a third-party model, available or not. **To unblock: load credits in the Cloudflare dashboard under AI Gateway.** What proves it worked: register one clip and watch its `annotationStatus` go `pending` → `ok` (`GET /api/clips/:id`); a clip stuck at `pending` means the consumer never ran, and `failed` means it ran and the answer did not parse — check the Worker's logs for which. Until then every registered clip stays `pending`, which is the designed behaviour, not a fault: annotation never blocks registration (§11).

- **The licence check only understands SPDX identifiers.** It compares each `license` field verbatim against an allow list of SPDX ids, so a package that spells its field loosely fails as unknown even when its licence is allowed. The first one vev meets is `hydra-synth`: the field reads `AGPL` where the `LICENSE` file is AGPL Version 3. Adding it in M1 fails `pnpm licenses:check` until `AGPL` is in the allow list in `scripts/check-licenses.mjs`, with that verification beside it. Add the exact string; do not loosen the comparison.

## Not wired yet

The preview environment (M1 task 6) is wired; production is M12's milestone. Before _that_ can work:

- `apps/api/wrangler.jsonc`'s top-level `database_id` (production, `vev`) is still a placeholder; `apps/api/drizzle.config.ts` has no `dbCredentials`, which `drizzle-kit push` and `studio` need.
- `apps/api`'s plain `deploy` script (production, unused by M1) still needs the SPA built first and `GIT_COMMIT` injected the same way `deploy:preview` does it — nobody has wired it because nothing runs it yet.
- `vev.0x7.sh` has no `routes` entry anywhere (see the gotcha above) — it arrives with the production environment, alongside a production Worker of its own.
- `THIRD_PARTY_NOTICES.md` (§4.1, §14.1) does not exist.
- Full Cloudflare Access JWT verification in the Worker (`apps/api/src/access.ts` is a presence check only — see the gotcha above for what's missing and why).
- An Access **bypass policy for `/api/health`**. The Worker already names it as its only public path, but Access intercepts at the edge before the Worker sees the request, so `https://vev-preview.0x7.sh/api/health` redirects to the login page and cannot be curled from CI or a script. Until a bypass (or service-token) policy scoped to that path exists, checking a promoted version's `commit` means opening a browser.
- A round trip through real Cloudflare Access. The guard is unit-tested only; no one has logged in to the preview and confirmed the Worker then sees a non-blank `Cf-Access-Jwt-Assertion` on an owner route (spec §17).
- ~~The `INGEST` queue's consumer handler (`queue()` export).~~ **Landed in M2** — `apps/api/src/index.ts` exports `queue` alongside `fetch`. The `deploy --env preview` trigger failure described in the gotcha above should therefore no longer appear; that has NOT been re-verified, because every deploy since has used `versions upload`, which does not touch triggers. The next `wrangler deploy --env preview` (or `wrangler triggers deploy --env preview`) is what confirms it.
