# Runbook

How to run vev locally and what bites. The design lives in [spec.md](./spec.md); decisions live in [adr/](./adr/README.md). This file is only what someone needs to operate the repository, and every entry was established by running it.

## Void

`apps/app` is the whole application — pages, Worker and queue consumer — on Void ([ADR 0011](./adr/0011-void-pages.md), [ADR 0009](./adr/0009-void-for-the-worker.md)). Worker bindings and the deploy targets live in `apps/app/deploy-targets.ts` (a module of their own so a test can read them), which `apps/app/void.config.ts` selects from by `VEV_TARGET` (`local` by default). Local D1, R2 and queue state live in `apps/app/.void/`. Use `void db migrate` for migrations and `void db execute <sql>` for local SQL, from `apps/app`.

**An existing checkout keeps its local data in `apps/api/.void/v3/`, which nothing reads any more.** Git removes the tracked files of `apps/api` and `apps/web` when you switch to this change, but leaves the untracked `.void/` and `node_modules/` behind. To keep the local D1, R2 and queue state: stop every `workerd` from this checkout, run `pnpm install` (it creates `apps/app/.void/`), then `mv apps/api/.void/v3 apps/app/.void/v3`. Then delete `apps/api` and `apps/web`. Starting from nothing is also fine: `pnpm live` re-applies the migrations to an empty database, and local data is scratch.

## Commands

| Command | What it does |
| --- | --- |
| `pnpm install --frozen-lockfile` | Installs; pnpm provisions Node itself. `apps/app`'s `prepare` script (`void prepare`) generates `.void/` (route and env types the typecheck needs); CI runs it explicitly after install, because pnpm skips lifecycle scripts when an install finds nothing to change. |
| `pnpm dev` | Development: one Vite dev server on `127.0.0.1:8787` serving the pages and the API together, one process. Applies local D1 migrations first. |
| `pnpm live` | Local mode (§15.3): builds the app (pages and Worker in one `vp build`), applies local D1 migrations, and serves the built Worker in workerd on `127.0.0.1:8787`, the same shape that deploys. |
| `pnpm check` | Typecheck, lint (oxlint) and format (oxfmt). |
| `pnpm test` | Every package's tests. `apps/app` runs two Vitest projects: `worker` (the Hono app and routes, inside workerd) and `client` (browser logic under `client/`, in Node). |
| `pnpm licenses:check` | Fails on a production dependency, or a dev dependency bundled for browsers, whose licence is not AGPL-3.0 compatible (§14.1). |
| `bash scripts/smoke-live.sh` | Starts `pnpm live` and asserts the single-origin contract: `/api/health` JSON, the stage's shell at `/`, old bookmarks redirecting to it, an unmatched path reaching the app's catch-all and loading the client script its shell names, a trailing-slash redirect, `404` for a missing file and for an unknown API route, and the page's shared commit matching `/api/health`. CI runs this. |
| `VEV_TARGET=preview pnpm --filter app run deploy` | `void deploy` for the preview target. Not yet run: linking the existing Worker comes first (ADR 0009). |

## Gotchas

Entries that name `wrangler` record what established them. Current commands are in the table above.

- **Delete a leftover `apps/api` or `apps/web` after pulling the one-package move.** Git leaves their untracked `.svelte-kit`, `build` and `dist` behind, and `pnpm check` then lints that generated code and reports tens of thousands of errors in files nothing imports.
- **Void defaults `workers_dev` and `preview_urls` to true, so every cloud target sets both to false.** Access protects only the custom domain, and the Worker's own guard checks only that an assertion header is present. `apps/app/test/deploy-targets.test.ts` fails if `preview` or `production` leaves either on. To see what Void actually emits for a target, run `VEV_TARGET=production pnpm exec vp build` in `apps/api` and read `dist/ssr/wrangler.json` (the keys are absent for `local`); rebuild with the default target afterwards, since `pnpm live` builds it anyway.
- **Keep `inference.bindings.ai` at `false` in `void.config.ts`.** Void otherwise infers an `AI` binding for the `local` target from `env.AI` in the source, and `vp preview` then opens a remote proxy session. With no Cloudflare credentials that session fails `pnpm live` (`it's necessary to set a CLOUDFLARE_API_TOKEN`), which is how CI found it, and a venue has no network to open it over (§15.3). Cloud targets declare `ai` in `deploy-targets.ts`, which keeps it. To reproduce without your login, run `bash scripts/smoke-live.sh` with `CI=1` and `XDG_CONFIG_HOME` pointing at an empty directory.
- **Keep `routing.notFound` at `none` in `void.config.ts`.** Void asks the assets again for a route's 404, so an asset-layer SPA fallback would turn an unknown `/api` path into a `200` page. There is no `index.html` to fall back to now; `pages/[...path]` is the app's fallback, and its loader throws a 404 for a path that names a file. The smoke check fails if either regresses (ADR 0011).
- **After a change to the `miniflare` / `workerd` overrides in `pnpm-workspace.yaml`, reinstall from scratch.** A stale symlink survives in an already-installed `node_modules`; neither `pnpm install` nor `pnpm install --force` clears it. `rm -rf node_modules && pnpm install` does. A fresh clone and CI are unaffected — the lockfile is correct.
- **Name the next migration**: `drizzle-kit generate --name <name>`. Without it drizzle-kit invents a name and the file has to be renamed and its entry in `migrations/meta/_journal.json` corrected by hand.
- **`TEST_MIGRATIONS` is a required member of the global `Cloudflare.Env`** (`apps/app/test/env.d.ts`), and `apps/app/tsconfig.json` compiles `src` and `test` as one program. Inert while production code reads bindings through Hono's typed `Env`; revisit if any code adopts `import { env } from 'cloudflare:workers'`.
- **A browser file and a Worker file need different tsconfigs, and a `.mjs` file needs one too.** `apps/app/tsconfig.json` loads `@cloudflare/workers-types` and has no DOM lib; `apps/app/client/tsconfig.json` is the browser's (DOM lib, no Worker types) and `apps/app/tsconfig.json` excludes `client/`. Without the split, `vp check` reports `HTMLCanvasElement` and `BroadcastChannel` as unknown in `client/`. `scripts/tsconfig.json` exists because, once `apps/web`'s tsconfig was gone, `scripts/check-licenses.mjs` reported `error typed` values from type-aware lint until it had a project of its own; why the fallback changed was not traced. `vp check` finds each file's nearest tsconfig, so a new top-level directory of TypeScript needs one of these too.
- **`.svelte` templates are outside the gate.** `pnpm check` reaches a component's `<script>` block with syntactic rules only — no template linting, no type-aware rules — because `svelte-check` cannot run against TypeScript 7 (see [ADR 0001](./adr/0001-vite-plus-toolchain.md)). Keep logic in `.ts` and components thin.
- **`pnpm check` prints only the formatting failure when there is one, and hides every lint error behind it.** `vp check` stops at the first failing stage, so a clean-looking "1 formatting issue" can sit on top of dozens of lint errors (53 did, on the control-screen branch). Run `pnpm exec vp check --fix` first, then `pnpm check`, and read the second one. The auto-fixer is not idempotent against every rule: it rewrites `() => Promise.resolve(x)` into `async () => x`, which `require-await` then rejects. Write the awaiting form (`async () => await x`) and it stays put.
- **`npx --package playwright@1.63.0` fails inside the repository with `EBADDEVENGINES`** when the shell's `node` is not the version `package.json` pins. Run the driver from a scratch directory with an absolute script path (`apps/app/e2e/README.md`).
- **`workerd` children can outlive a run.** After runs of `pnpm test` (and possibly `bash scripts/smoke-live.sh`, which was not traced separately) several process groups of `workerd` were left parented to init, started from this checkout's `node_modules`, none holding `:8787`. Find them with `ps -eo pid,ppid,pgid,etimes,cmd | grep workerd`, check the path is your checkout's, and stop them by process group; never `pkill`, because other projects run their own `workerd`.
- **Calling jev by hand: `cf ai run typesafe/jev-1.14.0 --body @request.json`.** It prints `{ state, result }` and `result` is what the Worker's `AI` binding is documented to return (`{ model, answers, usage }`). The request for a clip is easiest to produce by running `annotateClip` against a runner that writes its first `inputs` to a file, so the file is exactly what the Worker would send. A 320x180 image is refused (`[7003] ... Invalid image dimensions`); see [ADR 0010](./adr/0010-annotation-from-stills.md).
- **`pnpm check` can fail on a type-aware rule it passed a moment earlier.** `typescript(no-unnecessary-type-assertion)` fired on 2 of 6 runs of an unchanged file (`await response.json() as { id: string }` in a test) and on 0 of 8 after the cast was replaced by a `v.parse`. Parse instead of casting a `.json()` result and the rule has nothing to be inconsistent about; if a run fails with an assertion rule, run it again before editing code.
- **The stage has browser drivers, and they are manual on purpose** — `apps/app/e2e/`, with its own README. They open `/` in a real Chromium and assert on what is rendered, which is the half `vp build` cannot see: the `$effect` that refetches on a filter change, the refused-filter message, the reorder that has to survive a reload, the §14.2 refusal reaching the screen, choosing by click and by key, and the fade refusals being VISIBLE on the row. Start `pnpm live` first (they need the app and the API on one origin, and they seed their own fixtures into the local D1), then run them from a scratch directory with `npx --yes --package playwright@1.63.0 node <absolute path>/apps/app/e2e/<script>.mjs`. **If a driver misbehaves, look for an orphaned `workerd` before blaming it**: one holding `:8787` makes the next `pnpm live` die on bind, so the drivers hit the old Worker and a possibly stale build, and one holding an open handle on `apps/app/.void` keeps the OLD database alive after that directory has been renamed. Find them with `ps -eo pid,ppid,pgid,etimes,cmd | grep workerd`, and stop only your own by process group. `playwright` is deliberately NOT a dependency, and `apps/app/e2e/**` is excluded from lint in the root `vite.config.ts` for that reason. **They are not in `pnpm test` and not in CI**: they need a running server and, on a fresh machine, a few-hundred-MB Chromium download. Two things they do not prove: SwiftShader is a software rasteriser, so nothing there speaks to frame rate on a real projector; and `gl.readPixels` on the stage's canvas reads all zeros (`preserveDrawingBuffer: false`), so what the picture shows is evidence a human has to look at, except where a driver compares two screenshots of it.
- **A driver has to take the reload prompt.** The stage asks before a reload once the page has been interacted with (`beforeunload`), and Playwright dismisses a dialog nobody listens for, which cancels the navigation and hangs the driver. `openStage` in `lib.mjs` accepts them. A driver that compares the picture has to read a patch no overlay covers (`pictureFrame`), because the readouts change while the picture does not.
- **Screenshots under SwiftShader can take longer than the time left in a bar.** A driver that needs a card still outlined in its screenshot has to start early in the bar, or it captures the fade. `stage.mjs` waits on the Now overlay's bar phase.
- **A blocked `getContext` must cover `experimental-webgl` too.** regl tries both names, so a driver that refuses only `webgl` sees the probe pass on the fallback.
- **Access on `vev-preview.0x7.sh` covers the whole hostname, not a path list.** An unauthenticated `curl` on 2026-11-03 got a `302` to the login for `/`, `/studio`, `/output`, `/api/health`, `/media/x` and `/t/x` alike. So the stage moving to `/` needed no policy change there, and nothing is public yet, including what §13 calls public. The policy lives in the Cloudflare dashboard, not in this repository. Re-check with `curl -s -o /dev/null -w '%{http_code} %{redirect_url}' https://vev-preview.0x7.sh/`.
- **As of M2, `vev-preview.0x7.sh` sits behind Cloudflare Access, and `vev-preview.host3.workers.dev` no longer serves the app at all.** M1's "no Access yet, on purpose" state is over: Access binds to hostnames in the zone, so it protects the custom domain but can never protect a `*.workers.dev` hostname — the fix was to close that door instead (`env.preview.workers_dev` and `env.preview.preview_urls` are both `false` in `apps/api/wrangler.jsonc`). Requesting `vev-preview.host3.workers.dev` now returns Cloudflare's `error code: 1042` — the same signature the routes gotcha below describes, except this time it's deliberate. **This also means `/api/health` on the deployed preview now redirects to the Access login** (a browser-authenticated, manual check), and per-version `workers.dev` preview URLs (what `versions upload` used to print) no longer exist — the only surviving preview URL is the custom domain, and only a promoted version (`wrangler deploy` / `wrangler versions deploy`) is visible on it. `bash scripts/smoke-live.sh` is unaffected: it tests `pnpm live` (`--env local`, no Access), and CI is deliberately not changed to authenticate against Access.
- **The Worker also verifies `Cf-Access-Jwt-Assertion` itself (`apps/app/src/access.ts`), as defence in depth against Access being misconfigured off (§13) — but only as a PRESENCE check, not full verification.** It refuses (403) any request past `/api/health` that lacks a non-blank `Cf-Access-Jwt-Assertion` header; it does not decode the token or check its signature, issuer, audience or expiry. Full JWT verification (fetch and cache the team's JWKS from `ACCESS_TEAM_DOMAIN`, verify against `ACCESS_AUD`) was scoped as a stretch for the task that added this and did not land cleanly — two blockers, not code quality: (1) there was no way to obtain a real signed Access JWT to test against, short of driving a browser through Access's login flow, and (2) `curl` never reaches the Worker on the deployed preview to exercise it end-to-end, since Access's own edge redirect (302) happens before the request. Both `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` are already in `apps/api/wrangler.jsonc`'s `vars` (top level and `env.preview`) for whoever picks the stretch back up. **`ACCESS_TEAM_DOMAIN` is confirmed**: `https://vev-preview.0x7.sh/.well-known/cloudflare-access-protected-resource/` (unauthenticated) returns it directly as `team_domain`. **`ACCESS_AUD` is NOT independently confirmed** — it is the `kid` query param on the Access login redirect (`https://vev-preview.0x7.sh/` → `.../cdn-cgi/access/login/...?kid=<this value>`), which is very likely the application's audience tag but was not cross-checked against the Cloudflare dashboard, which is the actual source of truth. Verify it there before the stretch relies on it. The check is disabled whenever `VEV_MODE === 'local'` (local mode has no Access by design, §15.3) — **but the `apps/api` test pool's `VEV_MODE` is `'cloud'`, not `'local'`, despite `vitest.config.ts` reading the `development` configuration** (`vitest.config.ts`'s `miniflare.bindings` explicitly overrides `VEV_MODE` to `'cloud'`, the same way it overrides `GIT_COMMIT`). So the guard runs enabled in every `apps/api` test: any owner route Task 3 adds needs a real (non-blank) `Cf-Access-Jwt-Assertion` header in its test requests, or it 403s — do not "temporarily" disable the guard to make a red test pass.
- **The Worker's `env.preview` never points at the `vev` (production) D1 database** — it has its own `vev-preview` database (`bcee626b-7dbd-4456-8fb9-a708583e6e1d`), separate from `vev` (`6554a370-8884-4cbb-9f87-9d891a34ddcd`, reserved for M12). This is the whole reason the preview has its own `d1_databases` block instead of sharing the top-level one.
- **The Worker script has to exist before `versions upload` will work.** For a brand-new named environment, `wrangler versions upload --env preview` fails outright with "You cannot upload a new version of a Worker that does not yet exist. Please run the `deploy` command first." — there is no way around this with flags; a real `wrangler deploy --env preview` has to run once to create the script. (Before M2 this also created the `workers.dev` route; M2 turned that off — see the Access gotcha above.) This is a one-time bootstrap per environment (already done for `preview`); the repeatable `deploy:preview` script never needs to run it again.
- **Only one preview URL exists now: `vev-preview.0x7.sh`.** Before M2 there were two — a per-version `workers.dev` URL that `versions upload` printed fresh every run, and the stable `vev-preview.<subdomain>.workers.dev`/custom-domain URL that only a promotion moved. M2 set `env.preview.workers_dev` and `env.preview.preview_urls` to `false` (see the Access gotcha above), so per-version `workers.dev` URLs no longer print at all and the stable `workers.dev` hostname no longer resolves to the app (`error code: 1042`). `pnpm deploy:preview` (`versions upload`) uploads a version and prints only its Version ID — `wrangler versions list --env preview` lists uploaded versions but not which is live; `wrangler deployments status --env preview` (see the command table) is what shows the promoted version and its percentage, or check `/api/health`'s `commit` field once promoted (through a browser: it's behind Access now too). Promote with `wrangler versions deploy` (see the command table) to move `vev-preview.0x7.sh` to a new version; `deploy:preview` alone never does.
- **Adding `routes` to an environment silently disables `workers_dev` and `preview_urls` on the next triggers-changing deploy, unless you set them explicitly.** M1 verified this by accident (`workers_dev`/`preview_urls` defaulted to `false`, breaking `vev-preview.host3.workers.dev` with `error code: 1042`, until both were set back to `true`); M2 sets both to `false` on purpose, for the reason in the Access gotcha above — see there for the current, deliberate state.
- **`vev.0x7.sh` (no `-preview`) is deliberately not attached to anything.** That hostname is the production name; the production Worker does not exist yet (M12). Attaching it now would stand up a second Worker serving this same code against the production `vev` D1 database — exactly the duplication the separate `preview` environment exists to prevent.
- **`wrangler deploy --env preview` reported the `INGEST` queue's consumer trigger as failed, even though the deploy otherwise succeeded — because the Worker exported no `queue()` handler yet. It does now (M2); this should be gone, but has not been re-checked.** Verified while closing the workers.dev door for M2: `wrangler deploy --env preview` printed `Trigger configuration for "vev-preview" was only partially updated` with `Queue handler is missing` (code 11001) for the `INGEST` consumer, because no code in `apps/api/src` exports one yet. The Worker itself, its assets, the custom domain, the queue _producer_, and `workers_dev`/`preview_urls` all deployed fine regardless — wrangler says explicitly "Successful trigger changes were not rolled back." `wrangler versions upload` (`pnpm deploy:preview`) is unaffected: verified separately, it doesn't touch triggers at all (wrangler prints "Changes to triggers ... must be applied with `wrangler triggers deploy`"), so this only showed up on `deploy --env preview` or `wrangler triggers deploy --env preview`. The consumer handler has since landed, so the next triggers-changing deploy is expected to succeed cleanly — nobody has run one to confirm it (see "Not wired yet").

- **`typesafe/jev` is billed from prepaid AI Gateway credits.** The account now holds them, and `cf ai run typesafe/jev-1.14.0 --body @file.json` answers. `cf ai models` lists only the `@cf/` namespace, so its omission of a third-party model means nothing.

- **The licence check only understands SPDX identifiers.** It compares each `license` field verbatim against an allow list of SPDX ids, so a package that spells its field loosely fails as unknown even when its licence is allowed. The first one vev meets is `hydra-synth`: the field reads `AGPL` where the `LICENSE` file is AGPL Version 3. Adding it in M1 fails `pnpm licenses:check` until `AGPL` is in the allow list in `scripts/check-licenses.mjs`, with that verification beside it. Add the exact string; do not loosen the comparison.

## Not wired yet

The preview environment (M1 task 6) is wired; production is M12's milestone. Before _that_ can work:

- `void deploy` builds the app itself (Void's docs), so the old "build the SPA first" step is gone, and `void.config.ts` resolves `GIT_COMMIT` from git. Neither has been run against Cloudflare: no deploy was made when pages moved into `apps/app`.
- `vev.0x7.sh` has no `routes` entry anywhere (see the gotcha above) — it arrives with the production environment, alongside a production Worker of its own.
- `THIRD_PARTY_NOTICES.md` (§4.1, §14.1) does not exist.
- Full Cloudflare Access JWT verification in the Worker (`apps/app/src/access.ts` is a presence check only — see the gotcha above for what's missing and why).
- An Access **bypass policy for `/api/health`**. The Worker already names it as its only public path, but Access intercepts at the edge before the Worker sees the request, so `https://vev-preview.0x7.sh/api/health` redirects to the login page and cannot be curled from CI or a script. Until a bypass (or service-token) policy scoped to that path exists, checking a promoted version's `commit` means opening a browser.
- A round trip through real Cloudflare Access, to the stage at `/` now. The guard is unit-tested only; no one has logged in to the preview and confirmed the Worker then sees a non-blank `Cf-Access-Jwt-Assertion` on an owner route (spec §17).
- ~~The `INGEST` queue's consumer handler (`queue()` export).~~ **Landed in M2** — `apps/app/src/index.ts` exports `queue` alongside `fetch`. The `deploy --env preview` trigger failure described in the gotcha above should therefore no longer appear; that has NOT been re-verified, because every deploy since has used `versions upload`, which does not touch triggers. The next `wrangler deploy --env preview` (or `wrangler triggers deploy --env preview`) is what confirms it.
