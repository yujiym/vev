# 0001: The Vite+ toolchain

## Context

vev needs lint, format, typecheck and test working from the first commit, not bolted on once a milestone is under way. fuda-sh — a sibling project by the same author — already runs [Vite+](https://github.com/voidzero-dev/vite-plus) (`vp`) with the [ultracite](https://www.ultracite.dev/) lint/format presets, so that policy can be migrated wholesale rather than re-derived rule by rule. The alternative considered was assembling oxlint and oxfmt as direct dependencies alongside SvelteKit's own Vite setup and Vitest, configuring each by hand.

## Decision

Vite+ on the **0.3 line**, pinned to `0.3.3`, with the lint and format policy migrated from fuda-sh's root `vite.config.ts`.

`ErenayDev/viteplus-svelte` was read as a reference for the shape of SvelteKit running under Vite+ — the `vite@*` override redirecting to Vite+'s core, and the `sveltekit()` plugin wiring — and used only as a reference, never as a template: it ships no `LICENSE` file, and this repository is AGPL-3.0-or-later.

## Consequences

Measured on 2026-09-28, against what was actually installable:

- `vite-plus@1.0.0-rc.1` bundles Vitest 5.0.1. `@cloudflare/vitest-pool-workers@0.22.0` — the package that runs `apps/api`'s tests inside a real `workerd` — declares a peer of `vitest ^4.1.0`. The two cannot coexist in one lockfile, and 1.0 is still a release candidate. `vite-plus@0.3.3` bundles Vitest 4.1.11, oxlint 1.83.0 and oxfmt 0.68.0, all of which `ultracite@7.12.1` accepts (`oxlint ^1.79.0`, `oxfmt >=0.40.0`). This settled the 0.3-vs-1.0 choice: pinning 1.0 today would mean the Worker's test pool and the toolchain's own bundled test runner disagree on a major Vitest version, an incoherence `pnpm-workspace.yaml`'s `overrides` block cannot paper over the way it does for `oxlint`/`oxfmt`/`vite`.
- `pnpm-workspace.yaml` pins `oxlint`, `oxfmt` and the `vite@*` → `vite-plus-core` redirect as one `overrides` block, because they are `vite-plus@0.3.3`'s own dependency pins: bumping one without the others reintroduces the type mismatch Vite+'s `defineConfig` and ultracite's `OxlintConfig` type would otherwise disagree on. Revisit the 1.0 line once `@cloudflare/vitest-pool-workers` supports Vitest 5.
- The same `overrides` block also pins `miniflare`, `workerd` and the platform-specific `@cloudflare/workerd-*` packages upward, for an unrelated reason: `@cloudflare/vitest-pool-workers@0.22.0` bundles an older `miniflare`/`workerd` pair than `apps/api/wrangler.jsonc`'s `compatibility_date` needs. Without the override, the deployed Worker's compatibility date would have had to be lowered to whatever the test harness's bundled runtime supports — the wrong direction, since a test run exists to exercise the production runtime's semantics, not the other way around. Forcing the pool onto the newer `miniflare`/`workerd` already resolved elsewhere in the tree keeps the shipped compatibility date current instead.
- Adding those overrides to an _already-installed_ `node_modules` leaves a stale symlink behind: `pnpm install` rewrites `pnpm-lock.yaml` correctly, but the physical `node_modules/.pnpm/@cloudflare+vitest-pool-workers@.../node_modules/miniflare` symlink keeps pointing at the old version, and `pnpm install --force` does not fix it — only `rm -rf node_modules && pnpm install` relinks correctly. A fresh clone (and CI, which always starts from a clean checkout) is unaffected; this only bites a checkout that already ran `pnpm install` against the pre-override lockfile.
- `oxfmt` cannot format `.svelte` files until `svelte`/`svelte/compiler` resolves from somewhere in the dependency tree — it uses `prettier-plugin-svelte`, which requires `svelte/compiler` at runtime and does not bundle it. Setting `fmt.svelte: true` before any package declared a dependency on `svelte` broke formatting for _every_ file, `.svelte` or not, because oxfmt's formatting worker resolves that dependency eagerly for the whole run. `fmt.svelte` therefore stayed unset (scoped to a since-removed override) until `apps/web` existed and declared `svelte` as a dependency, at which point the top-level `fmt.svelte: true` started working without further changes, even though `svelte` is not hoisted to the repository root — the resolution mechanism by which oxfmt then finds it was not traced further.
- `svelte-check` — the tool that would type-check `.svelte` templates, filling the gap `oxlint` leaves (see §17) — refuses to run at all against this repository's TypeScript. It pins to TypeScript `^5.0.0 || ^6.0.0` and, seeing TypeScript 7 specifically, throws at startup demanding a second TypeScript major installed alongside (`typescript@~6` plus `@typescript/native@npm:typescript@7`, driven by `--tsgo`) rather than degrading gracefully. Carrying two TypeScript majors to appease one dev-only tool was rejected as a workaround worse than the gap it would close, so `svelte-check` is not part of `pnpm check`. This is a toolchain fact, not a validation-library one, so it is recorded here; its consequence — `.svelte` templates sit outside the type gate — is stated as a rule in `AGENTS.md` and in `CONTRIBUTING.md`.
